# 领克 05 真车性能实测与优化方案

日期：2026-10-30（Asia/Shanghai）。本报告补充并更新之前的静态排查，结论以本次实际安装包和有效采样为限。

## 结论

**当前卡顿应分成两部分处理：地图在本次场景下本身约 30fps，嵌入后又增加了帧间隔抖动；桌面持续翻页约 50–54fps，主要问题是少量长帧，而非一直只有十几帧。**

本次确认了现象所在的环节及资源占用，没有拿到完整 Dart 函数栈，尚不能把偶发长帧归因到某一个 Dart 函数。直接重写整个翻页系统、强制地图 60Hz 重绘或再大幅降低地图分辨率，都没有足够证据支持。

原始资料保存在 [live-2026-10-30](../car-reports/perf/live-2026-10-30/)；汇总：[summary.csv](../car-reports/perf/live-2026-10-30/summary.csv)，有效/排除样本清单：[evidence-index.json](../car-reports/perf/live-2026-10-30/evidence-index.json)。共保留 **15 组主要有效采样**，另有 1 组仅供参考的平移采样，7 组不纳入主要结论。

## 实测方法与结果

使用系统 atrace 的 gfx、input、view、sched、freq、idle、binder_driver、dalvik，结合 SurfaceFlinger 呈现时间戳。手势由临时 `app_process` helper 以约 60Hz 注入，每次 2.5 秒、150 个 MOVE，并打印设备 uptime 边界。统计仅截取操作窗口，未混入结束后等待时间。它不测触摸屏硬件采样，也不能替代真人体验。

CPU 由 sched 切换记录积分，**100% 表示一核，四核总计 400%**。atrace 切片是包含子项的墙钟耗时，不等于 CPU 时间。release 包没有完整 Dart build/raster 时间线，不能套用旧文档的 UI+raster 相加公式。

### 持续操作

| 场景 | 有效次数 | 操作窗呈现率 | 主要帧间隔 | 窗内最长帧间隔 |
| --- | ---: | --- | --- | --- |
| 共存版全屏地图拖动 | 3 | 29.58 / 29.54 / 29.56 fps | p50≈33.3ms；各轮 p90≈33.4–50.0ms | 50.1 / 50.0 / 66.6ms |
| 共存版嵌入，缩放 0.875，地图拖动 | 3 | 27.17 / 26.77 / 26.76 fps | p50≈33.3ms，p90≈50.0ms | 83.4 / 66.7 / 166.7ms |
| 淡入淡出，持续桌面翻页 | 3 | 52.32 / 50.26 / 54.33 fps | p50≈16.7ms；p90≈16.7–33.3ms | 66.7 / 66.7 / 50.1ms |
| 共存版嵌入，缩放关闭，地图拖动 | 2 稳态样本 | 26.78 / 27.15 fps | p50≈33.3ms，p90≈50.0ms | 83.3 / 116.7ms |

地图嵌入的呈现率取**桌面最终 Surface**；全屏取高德主要地图 Surface。嵌入虚拟显示中的高德 Surface 呈现另行保留，不能把它与 `consumedFrames` 或物理最终显示混为一个计数。不能据此计算精确“丢帧比例”。

这些是固定操作窗内的帧数/秒，包含手势刚开始的响应过程；同时列出帧间隔分布，避免仅凭平均值掩盖长帧。地图全屏与嵌入的分辨率、视野、界面布局不同，因此是使用场景对比，**不是隔离单一变量的合成开销实验**。新装地图也出现过新功能提示、位置选择卡片，截图已保留；后台应用没有被统一关闭。

结论：地图拖动整体节奏约为 30fps，嵌入后的主要退化表现为更不均匀的呈现。关闭缩放没有显示出稳定帧率优势；稳态样本只有两组，不能宣称 0.875 带来某个精确百分比收益。保留原来的开启状态比较合理。

### 线程与后台负载

| 场景 | 桌面进程 CPU | 共存版地图 CPU | 可见情况 |
| --- | --- | --- | --- |
| 全屏地图拖动 | 约 4.7–6.8% | 约 83–95% | 地图全屏，桌面窗口隐藏，底栏仍在 |
| 嵌入地图拖动 | 约 48–52% | 约 66–79% | 桌面主线程约 21%、raster 约 18%（首轮示例） |
| 淡入淡出翻页 | 约 74–82% | 约 12–19% | raster 约 40–43%，主线程约 29–32% |
| 地图页空闲（单轮） | 约 25.6% | 约 19.6% | 桌面约 4 presents/s，不能当作交互掉帧 |
| 切到另一页空闲（单轮） | 约 15.2% | 约 17.2% | 地图 cardVisible=false，地图进程仍有负载 |

相同采样窗口中，语音进程捕获线程常占约 16–20% 单核 CPU；原来的高德 7.5 进程仍存在，部分窗口占约 7–10%；logd/logcat 及车辆系统服务也占资源。另有一轮浏览器后台 CPU 升高。这些是可观测的竞争负载，**尚未做停启对照，不能把它们直接判为卡顿根因，也没有擅自关闭语音/原车服务**。

嵌入操作确实让桌面和 SurfaceFlinger 承担额外工作，但 CPU 占用并不支持“四核已经全部耗尽”的说法。应优化关键线程的及时性，而不是只看总 CPU 百分比。

### 输入与点击

嵌入地图时，每轮约 136–138 个 `DartMessenger#handleMessageFromDart on .../map/0` 切片进入 Android 主线程；首轮平均约 1.65ms，第三轮最大约 14.05ms。这证明输入桥有成本，但没有显示每个调用都阻塞几十毫秒。通道计数不严格等于 MOVE 数，Android 输入自身也可能合并事件。

两轮点击页码均确认切页。第一帧在按下后约 53ms / 109ms 出现，但点击持续约 50ms，且第一帧可能属于按下反馈/其他更新，**不把这两个数字宣称为精确的端到端点击延迟**。动画期间大部分间隔约 16.7ms，最大约 50ms；不以固定 500ms 点击观察窗计算“动画 FPS”。

当前 [LiveNavigationHost.java](../app/android/app/src/main/java/xyz/i4o/uni/launcher/platform/LiveNavigationHost.java) `touch()` 使用收到事件时的 `SystemClock.uptimeMillis()` 构造 MotionEvent；[embedded_navigation.dart](../app/lib/widgets/embedded_navigation.dart) 的触摸 payload 没有携带原始时间。这使排队延迟难以追踪，也可能在批量到达时改变下游的速度估计。**这是确定存在的设计问题，但尚未量化它对体感的贡献。**

### 内存和 GC

地图拖动采样前 `MemAvailable` 约 1.36GB。一次内存快照中，桌面 PSS 约 254MiB，共存版地图约 416MiB，Swap PSS 分别只有几十 KB。没有本次内存不足的直接证据。

桌面有频繁的后台并发 GC，例如 2.5 秒内 3 次，但不能把 30–50ms 的后台 GC 总时长当作 UI 停顿。观察到的 `(Paused)` 子阶段多为亚毫秒至约 1ms，不能据此解释 166ms 的整个长帧。对象分配仍值得优化，但优先级应低于输入和呈现节奏。

## 可执行的优化方案

### 第一步：优先解决地图跟手性，先把排队与绘制分开

目标是减少 67–167ms 的长间隔，并让嵌入后的节奏更接近本次全屏约 30fps；不是让 Flutter 重复绘制同一地图纹理来伪造 60fps。

1. 在 `embedded_navigation.dart` / `LiveNavigationHost.java` 给触摸增加 sequence、原始事件时间、入队/出队时间；把时钟校准为 Android uptime 域，保留原始 downTime/eventTime。记录地图回调、纹理可用/消费时间，但分别命名，避免再次混淆生产、消费、呈现。
2. 做一个独立实验：输入转发改成串行且队列有界，连续 MOVE 只保留最新待处理位置，DOWN/UP/CANCEL 与多指变更必须保持顺序；不再为落后的坐标无限排队。若用帧调度，应显式请求帧，不能只依赖 `addPostFrameCallback`。优先保留不超过 60Hz 的输入能力，不直接降到 30Hz。
3. 对输入回调、状态快照/序列化、Dart 构建、raster 分别加测量标记。用同场景诊断构建找出 166ms 缺口中的等待；只有确认主线程转发是主要耗时后，才将可迁移部分放到专用串行线程，并加会话 generation 与取消保护。

验收：三轮连续地图拖动中，p90 和 >50ms 间隔数量相对基线下降；低帧率时不积压手势，不出现抬手跳变、双指错序、离开页面后继续注入。主观跟手性和物理触摸需另行人工验收。

### 第二步：减少后台资源占用与分配

依据是地图隐藏后仍有 CPU、桌面并发 GC 频繁，以及已有多个状态订阅/窗口；具体收益仍需单项对照。

- 审计 `LauncherRuntime`、`MainActivity.updateSnapshot`、`GlobalDockService` 对同一次状态更新的重复快照、JSON 构造与发送。保留现有节流和选择性通知，在测到热路径后复用不变数据或按窗口订阅变化字段；不要再直接假设每包都是旧版的 805KB。
- 给隐藏地图设计可恢复的渲染降载策略，验证 Android 9 的显示/Surface 生命周期。地图导航播报和路线计算必须继续，不能用 force-stop 地图来换低 CPU。
- 单独测量语音捕获线程与日志的负载来源，再调整音频缓冲、处理周期或日志频率。原车服务及语音功能不可为了跑分直接关掉。

验收：隐藏页与空闲页 CPU、对象分配下降；地图恢复后第一帧及时、无黑屏/重启导航；语音唤醒、路线播报与底栏功能正常。

### 第三步：针对翻页长帧，而非推倒现有页面复用

当前有效翻页约 50–54fps，已有页面子树和 RepaintBoundary。先在 profile 时间线中分清首帧构建、持续 raster、透明合成和调度等待，再选择动作：

- 若首次进入页资源创建明显，预热已知图片/SVG，避免在手势开始时同步做大工作。
- 若透明合成是主因，再用相同地图界面重复比较淡入淡出与平移，或缩小透明合成范围。
- 若后台状态刷新与长帧重叠，先缩小刷新影响范围和减少分配；没有 cache miss 证据前不强制两页截图。

验收：持续翻页稳定接近 60Hz，重点减少 >33ms、>50ms 间隔；快慢拖动、反向取消、地图页进出均不重建地图。不能以只有一轮的“平移更快”作为上线依据。

### 当前设置建议

保留深蓝玻璃、无实时模糊、地图缩放开启。淡入淡出已经恢复；本轮没有充分证据要求改为平移。地图自身约 30fps 的原因可能涉及其运行档位或渲染工作量，**本次未证明是硬限帧**，不修改用户地图 APK，也不承诺修改桌面就能让地图达到 60fps。
